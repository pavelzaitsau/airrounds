# T13 board flashing, self-test, and CI release

T13 lets the Flipper app flash and test the ESP32-S2 Devboard on its own, and
adds a CI release. The release bundles the Flipper `.fap` with the Devboard
firmware image, so an operator installs one package and flashes the board from
the Flipper, with no Mac and no `esptool`. The public release carries the passive
receive-only image. The active transmit image builds only with an opt-in compile
flag, and the public build leaves it off.

T13 fills the two empty Flipper menu entries from T10: **Flash board hardware**
and **Test board**. It adds a microSD preflight that the [T12 bench][t12-bench]
recorded as missing. This phase writes the requirements. It writes no firmware
code; the design and the architecture follow in later stages.

## Release image and the active opt-in

The public release flashes the passive receive-only image. Receive-only is the
project default in `AGENTS.md` and [acceptable use](acceptable-use.md), and the
public build holds to it.

The active transmit image builds only with the opt-in compile flag
`-DAIRROUNDS_ACTIVE=1`, the same gate as [T12](t12.md). The public release leaves
the flag off and ships no active image. An operator who builds with the flag
flashes an active image at their own risk.

A flash of an active image must gate behind the active-mode attestation from
[acceptable use][aup-active], so the operator confirms the active limits before
the Flipper writes the image. A passive flash needs no attestation. See
[open questions](#open-questions).

## Approved decisions

A requirements survey settled seven decisions. Each one binds the design and the
architecture.

| Decision | Choice |
| --- | --- |
| Flash model | The Flipper flashes the ESP32-S2 over UART through the ROM serial bootloader. |
| Bootloader entry | Automatic. The Flipper drives IO0 and EN to enter and leave the bootloader. |
| Release image | The passive receive-only image. The active transmit image builds only with the opt-in `-DAIRROUNDS_ACTIVE=1` flag, off in the public build. |
| Test board | A full self-test: connect, firmware version, microSD, radio, and a verified test PCAP write. |
| microSD absent | Scan and Capture refuse with an explicit error. Flash board and Test board still run. |
| Firmware delivery | The ESP image ships on the Flipper microSD beside the `.fap`, not compiled into the `.fap`. |
| CI | GitHub Actions on a Linux x64 runner. |

## Workstreams

T13 has four independent workstreams. The CI build (W1) produces the artifact
the flasher (W2) consumes. The self-test (W3) and the microSD gate (W4) share
the protocol change but ship independently.

### W1: CI release build

The CI build runs the host gate and produces the release bundle.

- Port the toolchain to Linux x64: Arduino CLI 1.6.0, ESP32 core 2.0.11, Xtensa
  GCC 8.4.0, Python esptool 4.5.1, and `ufbt` with the pinned f7 SDK 1.5.1. The
  current toolchain in `.airrounds-tools` is arm64 macOS only.
- Run `make check`, `make asan`, and `make tsan` on the runner's LLVM.
- Run `make embedded` to build the passive ESP image and the `.fap`. The active
  image builds only in the opt-in `-DAIRROUNDS_ACTIVE=1` build, not in the public
  release.
- Merge the image offsets into one `airrounds.bin` at offset `0x0`, so the
  flasher writes one region. Record its SHA-256 and MD5.
- Write a manifest: the source build ID, the Git revision, the firmware and app
  versions, and the image hashes.
- Publish the `.fap`, the merged image, and the manifest to a GitHub release on
  a version tag.

The opt-in active build needs `-DAIRROUNDS_ACTIVE=1` and `-Wl,-zmuldefs`, which
`tools/quality/embedded.py` already applies to the `airrounds_active` sketch. The
public release does not build that sketch.

### W2: Flipper flasher

The Flipper flashes the board over its UART pins, with no host tool.

- Enter the bootloader: the Flipper drives IO0 low and pulses EN, then releases
  IO0. The pins route to Flipper GPIO; the mapping is an open question for the
  bench.
- Run the ESP32-S2 ROM serial loader over UART: `SYNC`, `FLASH_BEGIN`,
  `FLASH_DATA` with SLIP framing and per-packet checksum, then `FLASH_END`. Use
  the raw ROM loader, with no stub and no compression.
- Stream the release image from the Flipper microSD, so the Flipper never holds
  the whole image in RAM.
- Verify the written image with the ROM `SPI_FLASH_MD5` command against the
  manifest MD5. A mismatch fails the flash and keeps the error on screen.
- Reset the board into the application after a verified write: drive IO0 high and
  pulse EN. A failed or unverified flash leaves the board in the bootloader,
  reflashable on a retry, so a bad write never bricks the board.
- Show progress and a terminal state: in progress, verified, or a named error.
- Gate the flash behind the active-mode attestation when the image is an active
  build. A passive flash needs no attestation.

### W3: Board self-test

The firmware gains a self-test command, and **Test board** drives it.

- Add a UART `selftest` command, scope zero, behind a new feature bit. An older
  board without the bit reports the test as unsupported.
- The board runs, in order: a microSD mount check, a radio init check, a short
  receive probe, and a test PCAP write that the board reopens and verifies.
- A failed check reports its own result and blocks the checks that depend on it.
  A failed microSD mount reports the test PCAP write as blocked, not failed.
- The reply carries a per-check result. The Flipper shows each check with a pass
  or fail label.
- The board removes the test PCAP after the check, so the self-test leaves no
  capture on the card.

### W4: microSD gate

The app blocks capture without a card and warns before a round.

- The board reports microSD status in its status reply. The app blocks Scan and
  Capture with an explicit "no card" error, and leaves Flash board and Test
  board available.
- Add a round preflight: the board checks the card before it starts listening,
  and reports a missing or unmountable card before the round, not at save time.
  Without this, a round runs to completion and saves nothing, reported late as
  `storage_error`. The [T12 bench][t12-bench] saw this.

## Out of scope

- A board without a microSD card. The card stays required. A later version adds
  an on-board capture buffer for a card-less round.
- A public release of the active image. The active build stays opt-in and local,
  behind the `-DAIRROUNDS_ACTIVE=1` flag.
- Over-the-air or USB flashing. The Flipper flashes over UART only.
- A stub flasher or image compression. The raw ROM loader writes the whole
  image uncompressed.
- A flash-before-write backup of the board. Recovery from a failed flash is a
  re-flash, which the bootloader always allows after a failed write.

## Constraints

- **Clean-room flasher.** `esp_flasher` and `esptool` are the reference for the
  ROM protocol wire format, which is the public ESP32-S2 ROM serial loader
  specification. Implement the protocol from that specification. Copy no GPL
  code into the tree; see [acceptable use][aup-third-party].
- **Active transmit risk.** The opt-in active build flashes a transmit firmware.
  The FCC treats Wi-Fi deauthentication as prohibited jamming under 47 U.S.C.
  section 333, and the operator carries that risk. The public release ships no
  active image. See [active operation][aup-active]. This document is not legal
  advice.
- **Bootloader entry depends on wiring.** The automatic entry needs the Flipper
  to control IO0 and EN. If the Devboard does not route both to Flipper GPIO,
  the flasher falls back to a manual BOOT-and-RESET prompt. The bench confirms
  the wiring.
- **Linux build reproducibility.** The Linux toolchain must produce an image the
  pinned esptool verifies. Pin every tool version, so the CI image matches a
  local macOS build within the manifest hashes, or the manifest records the
  per-platform difference.

## Acceptance criteria

- The CI build runs on a Linux x64 runner, passes `make check`, `make asan`, and
  `make tsan`, and publishes the `.fap`, the merged passive image, and the
  manifest to a GitHub release.
- The Flipper flashes the release image over UART and verifies it with the ROM
  MD5, with no host tool.
- **Test board** runs the full self-test and shows a result for each check.
- Scan and Capture refuse without a microSD card, with an explicit error. Flash
  board and Test board run without a card.
- A round started with no card warns the operator before it listens.
- A flash of an opt-in active image gates behind the active-mode attestation. A
  passive flash does not.
- A bench run on the Devboard flashes the board from the Flipper, passes the
  self-test, and then captures a handshake on an own WPA2-PSK network.

## Acceptance status

The code is complete and every host gate passes. The firmware adds the `card` and
`selftest` commands and the microSD round preflight behind feature bit 6. The
Flipper adds the Test board screen, the Scan and Capture card gate, and the Flash
board screen with the active-image attestation and the ROM flasher. The CI
release builds and packages the passive image and the manifest.

| Check | Status |
| --- | --- |
| `make check`, `make asan`, `make tsan` | Pass on the 23.1.6 toolchain. |
| `make embedded` | Builds the ESP images and the `.fap`; the Flipper app stack stays within budget. |
| CI release packaging | `tools/ci/package-release.py` merges the image and writes the manifest; the flasher parses that manifest. |
| ESP image on hardware | The merged image flashed to the Devboard over USB and `esptool` verified the written hash. |
| Flipper app on hardware | The `.fap` installed and launched on the Flipper, which polls the Devboard over the UART. |
| Test board on hardware | The self-test reports microSD, Radio, Receive, and Write all Pass. |
| Card gate on hardware | Scan lists beacons with a card present; with no card at connect, Scan and Capture show "Insert SD card". |
| Self-test with no card | microSD reports Fail and the test PCAP write reports Blocked, not Fail. |
| Flash board on hardware | The flasher parses the manifest, syncs the ROM loader, writes the image, and runs the MD5 verify. |

A bench run found and fixed two defects the host gate could not catch:

- The self-test Write check failed because `SD.open` doubled the card
  mountpoint. The self-test now writes through the POSIX card path, and Write
  reports Pass.
- The flasher read the manifest into a 256-byte buffer and truncated the
  347-byte CI manifest before its md5, so Flash board showed "No image". The
  buffer is now 512 bytes, and the UI emulator guards the size.

## Bootloader entry on this Devboard

The automatic entry does not drive this Devboard. The `gpio_ext_pc0` and
`gpio_ext_pc1` pins do not reach its IO0 and EN, so the flasher's boot pulse is a
no-op and the first sync fails. Manual entry is the supported path: on a sync
failure the Flash board screen prompts "Hold BOOT, tap RESET", and the sync
retries catch the loader the operator entered by hand. A later Devboard that
routes IO0 and EN to Flipper GPIO can set the two pins and regain automatic
entry.

Open bench items, which need the Flipper buttons and the Devboard in hand:

- Transfer robustness is a deferred follow-up. The ROM write over the Flipper
  UART failed the final MD5 once on a full run. The per-block XOR-8 checksum
  passed every block, so the MD5 caught an undetected UART bit error. The flash
  fails safe and stays reflashable; a more robust transfer (lower baud, flow
  control, or verified responses) comes after CI.
- The CI release workflow runs on a Linux x64 runner, where the LLVM and
  Cppcheck patch pins and the merge offsets still need confirming.

## Open questions

| Question | Owner |
| --- | --- |
| Where does the active image live on the Flipper microSD? | Architecture |
| The active-mode attestation UX before an opt-in active flash. | Design |
| The version bump for the T13 release. | Release |

The bench answered two earlier questions. IO0 and EN do not route to
Flipper-controllable GPIO on this Devboard, so the flasher uses manual entry.
The ROM loader runs at 115200 baud over the Flipper UART, the rate the app
already uses.
